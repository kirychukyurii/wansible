# Webitel Ansible: редизайн під 26.4 + фундамент для HA

- **Дата:** 2026-06-10
- **Статус:** Draft (на рев'ю)
- **Репо:** wansible
- **Джерела:** Confluence "Changelog: GitHub Actions / підтримка Debian 13", "Upgrade Notes 26.02-26.4", "Failover (single DC)"; репо `deployment` (v25.08); репо `patroni-cluster` (bash-скрипти HA + Nomad job specs)

## 1. Контекст і мотивація

Поточний wansible розгортає Webitel v23.09 і не сумісний з 26.4:

| Аспект | Зараз (23.09) | Потрібно (26.4) |
|---|---|---|
| APT-репо | `deb.webitel.com` (user/password, auth.conf.d) | S3-репо `s3://webitel-apt-repo` через `apt-transport-s3`, AWS-креденшіали, новий GPG-ключ, компонент `26.4-releases` |
| ОС | Debian 11 (жорстка перевірка) | Debian 12 (bookworm) + PG 15 **або** Debian 13 (trixie) + PG 18 |
| systemd-юніти | копіюються з `/opt/webitel/etc/systemd`, патчаться `replace`/`lineinfile` | їдуть у deb-пакетах; maintainer-скрипти створюють юзера, роблять enable/restart; нові імена `webitel-*.service` |
| PostgreSQL | `webitel-postgresql-15` (екстеншн + міграції) | `webitel-postgresql-{15,18}` (екстеншн) + окремий `webitel-postgresql-migrations` |
| Сервіси | core, engine, call_center, flow_manager, storage, messages, logger | + cases, media-exporter; опціонально portal, fts, wfm, dsa, meetings, webrtc-rec, im-* (6), ai-amd |
| Frontend | пакети без суфікса | пакети `*-app` (`webitel-crm-app` тощо) |
| Реплікація PG | main/standby через pg_basebackup, без failover | Фаза 2: Patroni-кластер |
| Consul/RabbitMQ | рівно один хост (preflight фейлиться на >1) | Фаза 2: кластери 3+ нод |

Додатково накопичився технічний борг: `apt_key` (видалений у ansible-core 2.17+), вкладені імена ролей `webitel/engine` (ламають ansible-lint), `.bootstrap`-файли замість ідемпотентності, конфігурація через regexp-патчинг файлів.

**Рішення: редизайн репозиторію з нуля, з 26.4 як першим наповненням.** Від старих ролей у 26.4 лишається мало (пакети самі ставлять юніти і юзера), тому еволюція старого каркаса зекономила б мізер, законсервувавши застарілу структуру.

## 2. Ухвалені рішення (з обговорення)

1. **Редизайн зараз**, а не еволюція: нова структура, стандартні inventory-групи замість `webitel_services`+`group_by`.
2. **Розкладка сервісів по хостах — повністю через інвентар**: кожен сервіс = група + тонка роль; нічого не ставиться неявно; один хост може бути у багатьох групах.
3. **ОС/PG матриця: обидві комбінації** — Debian 12+PG15 і Debian 13+PG18; `pg_major` обчислюється з Debian release; preflight фейлить непідтримувані комбінації та не-amd64 для PG-екстеншна і FreeSWITCH.
4. **Тільки чиста інсталяція.** Оновлення існуючих інсталяцій 23.x/25.x → 26.4 — за ручними Upgrade Notes у Confluence. Плейбук не реалізує pg_upgrade / dist-upgrade / перейменування юнітів.
5. **Patroni DCS залежить від схеми**: Consul KV для single-DC (Failover) та per-DC кластерів (Warm standby 2 ДЦ); **etcd** — обов'язковий для stretch-Patroni у 3 ДЦ (Consul завжди per-DC, його KV не реплікується між ДЦ). Фаза 2 реалізує Consul KV; etcd — фаза 3.
6. **Власні тонкі ролі, не коммюніті-ролі** для consul/nomad/patroni/rabbitmq. Причини: власний `nomad-systemd-driver-plugin`, специфіка TimescaleDB+webitel-екстеншн, TLS зі свого CA, node pools; коммюніті-ролі великі і напівзакинуті. Коммюніті-**колекції модулів** (`community.rabbitmq`, `community.postgresql`, `community.general`, `ansible.posix`) — використовуємо, з пінінгом версій. Для Patroni-деталей підглядати у `vitabaks/autobase`.
7. **Nomad у фазі 2 — тільки інсталяція** (server + client на всіх нодах + systemd-driver-plugin). Nomad jobs (зокрема multi-DC схема, count-per-node, floating IP) — окрема фаза 3. Цільова модель: ВСІ Webitel-сервіси з часом керуються Nomad (десь count=1, десь на всіх нодах).
8. **Пакування: репо плейбуків**, структурно сумісне з майбутньою конвертацією в Ansible Collection (плоскі snake_case ролі, префіксовані змінні, FQCN, без вкладених ролей).
9. **Тести: lint + syntax-check у CI з фази 1; Molecule — разом із кластерними ролями у фазі 2.**

### Модель інвентаря

**Хост-центрична: сервіси додаються до сервера, а не сервер до сервісів.** Людина описує кожен хост одним блоком зі списком `services`; повноцінні Ansible-групи з нього матеріалізує `constructed` inventory plugin на етапі парсингу інвентаря (не runtime `group_by`, як зараз):

```yaml
# inventories/production/01-hosts.yml — єдиний файл, який редагує людина
all:
  hosts:
    node1:
      ansible_host: 10.20.0.10
      datacenter: kyiv            # опційно; дефолт dc1
      services:
        - consul_server
        - rabbitmq
        - patroni
        - webitel_engine
        - webitel_cases
    node2:
      ansible_host: 10.20.0.11
      datacenter: kyiv
      services: [freeswitch, webitel_storage, webitel_flow_manager]
```

```yaml
# inventories/production/99-constructed.yml — статичний, не редагується
plugin: ansible.builtin.constructed
strict: true
keyed_groups:
  - key: services
    separator: ""        # елемент списку = ім'я групи: consul_server, rabbitmq...
  - key: datacenter
    prefix: dc           # бонусом групи dc_kyiv, dc_lviv
```

Властивості та запобіжники:

- групи існують на момент парсингу → plays таргетять `hosts: webitel_engine`, працює `--limit`, застосовуються `group_vars/<група>.yml` (на відміну від runtime-груп `group_by`);
- один рядок у `services` = сервіс на хості; "що живе на сервері" видно одним поглядом;
- **preflight валідує `services` проти білого списку відомих сервісів** — typo дає fail із переліком валідних імен, а не тиху відсутність хоста в групі;
- підсумкова топологія — через `ansible-inventory --graph` (документується в README);
- constructed мерджиться зі статичними групами — класичний груповий стиль доступний як запасний;
- імена сервісів/груп — snake_case (валідні Python-ідентифікатори);
- singlehost = один хост із повним списком `services`; HA-приклади — ті самі файли з більшою кількістю хостів.

**Вимір "датацентр".** ДЦ — атрибут хоста (`datacenter`, дефолт `dc1`):

- single-DC інвентарі взагалі не згадують ДЦ;
- **кластеризація per-DC — дефолтна поведінка ролей** (peer-список = "члени моєї групи в моєму ДЦ", див. конвенцію нижче) → warm standby 2 ДЦ не потребує нічого, крім проставленого `datacenter` на хостах;
- stretch — єдиний явний виняток: `patroni_cluster_scope: global` + `patroni_dcs: etcd` у group_vars;
- валідації рахуються з `hostvars[*].datacenter` — жодних конвенцій імен груп.

### Конвенції ролей

Скелет (файли опціональні, якщо порожні):

```
roles/<role>/
  defaults/main.yml       # всі перевизначувані змінні, префікс <role>_
  vars/main.yml           # внутрішні константи — рідко
  tasks/
    main.yml              # тільки include_tasks: validate → install → configure
    validate.yml          # assert на вхідні змінні ролі
    install.yml           # apt/get_url
    configure.yml         # dirs, templates, enable
  handlers/main.yml       # рестарти, через listen
  templates/              # ім'я = цільовий файл: consul.hcl.j2
  files/
  meta/main.yml           # без dependencies
  README.md               # таблиця змінних
```

Правила:

1. **Без `when: inventory_hostname in groups[...]` всередині ролей** — таргетинг роблять plays (`hosts: <група>`).
2. **Змінні з префіксом ролі**; усе перевизначуване — у `defaults/`. Крос-рольові факти (DSN-и, адреси) обчислюються у `group_vars`/play vars і передаються ролям як їхні змінні — роль не лазить у `groups[...]` сама.
   **Peer-списки кластерів — теж змінні з дефолтом**, а не жорсткі `groups[...]` у тасках. Дефолт — "члени моєї групи в моєму ДЦ", тож per-DC кластеризація автоматична, а single-DC поводиться як вся група:
   ```yaml
   # defaults/main.yml
   rabbitmq_cluster_hosts: "{{ groups['rabbitmq']
     | map('extract', hostvars)
     | selectattr('datacenter', '==', datacenter)
     | map(attribute='inventory_hostname') | list }}"
   ```
   Stretch-випадок перевизначає scope явно (`patroni_cluster_scope: global`). Некрасива jinja живе тільки в `defaults/` — користувач інвентаря її не бачить. Аналогічно: `consul_server_hosts`, `patroni_cluster_hosts`, `nomad_server_hosts`, `etcd_cluster_hosts`.
3. **Хендлери через `listen`**, notify за зміною шаблону. Жодних `.bootstrap`-файлів — ідемпотентність дають шаблони + handlers.
4. **Теги** `<role>_install` / `<role>_configure`; `validate.yml` — `tags: [always]`.
5. **Плоскі snake_case імена ролей** (`webitel_engine`), сумісні з ansible-lint `role-name` і колекціями.
6. **Шаблони — повний файл** з `# {{ ansible_managed }}`. Ніяких `lineinfile`/`replace` по файлах з пакетів: якщо конфіг наш — він повністю наш.
7. **meta/dependencies не використовуємо** — порядок видно лише в site.yml.
8. **FQCN скрізь**; check-mode дружність (`changed_when` для command, модулі замість shell де можливо).
9. **Vault-патерн**: секрети у `group_vars/all/vault.yml` зі змінними `vault_*`; відкриті файли маплять: `webitel_repo_s3_secret_key: "{{ vault_webitel_repo_s3_secret_key }}"`. У репо — лише `.example`.

## 4. Фаза 1 — розгортання Webitel 26.4 (single/multi-host, без HA)

### 4.1 Роль `base`

- спільні пакети (acl, curl, gnupg, locales, python3-psycopg2, ...), locales_gen, sysctl (file-max, max_map_count, disable_ipv6);
- **S3 APT-репо Webitel**: `apt-transport-s3`; `/etc/apt/s3auth.conf` (mode 0600) з `AccessKeyId`/`SecretAccessKey`/`Region=eu-central-1` зі змінних; GPG-ключ: ASCII-armored `files/webitel-apt-repo.gpg.pub` → `gpg --dearmor` → `/usr/share/keyrings/webitel-apt-repo.gpg`; sources: `deb [signed-by=...] s3://webitel-apt-repo {{ ansible_distribution_release }} {{ webitel_release_component }}` (default `26.4-releases`; компонент `main` — опційно другим словом);
- видалення слідів старого репо відсутнє — чиста інсталяція.

### 4.2 Preflight (`playbooks/preflight.yml`)

- Debian 12 або 13; інакше fail з повідомленням;
- обчислення `pg_major`: bookworm→15, trixie→18 (set_fact, доступний всім);
- amd64-перевірка для хостів груп `postgres`/`patroni` (webitel-екстеншн) і `freeswitch` (модулі);
- не-HA обмеження: по одному хосту в `rtpengine`, `opensips`, `postgres` (поки нема Patroni);
- обов'язкові секрети: S3-креденшіали, `freeswitch_signalwire_key`;
- консистентність груп: `nginx_letsencrypt` ⇒ `nginx_site_name`+`nginx_mail_address` тощо (перенос поточних перевірок).

### 4.3 Зовнішні репозиторії (по ролях, не в base)

Кожна роль додає свій репо keyring-файлом + `signed-by` (без `apt_key`): postgresql.org + timescaledb (роль postgres), HashiCorp (consul/nomad), SignalWire (freeswitch), Sipwise mr11.x (rtpengine — версію репо звірити на актуальність), OpenSIPS apt (версію звірити: зараз 3.2, перевірити цільову для 26.4), RabbitMQ novemberain, Grafana.

### 4.4 Роль `postgres` (standalone)

- `postgresql-{{ pg_major }}`, `timescaledb-2-postgresql-{{ pg_major }}`, `webitel-postgresql-{{ pg_major }}`, **`webitel-postgresql-migrations`**;
- `timescaledb-tune --pg-version={{ pg_major }}`;
- listen_addresses + pg_hba для хостів інвентаря (шаблоном або postgresql_* модулями);
- юзер `opensips`, БД `webitel`, restore схеми з шляхів пакета (звірити фактичні шляхи у 26.4: `/usr/share/postgresql/{{ pg_major }}/webitel/...`);
- cron database_helper;
- БЕЗ main/standby реплікації (її замінить Patroni у ф.2).

### 4.5 Роль `consul`

- одна роль, `consul_role: server|agent` визначається членством у групі (server у ф.1; agent-режим використовується з ф.2);
- HCL-шаблон `/etc/consul.d/consul.hcl` замість JSON; bootstrap_expect = `groups['consul_servers'] | length`;
- bind/client_addr: localhost для singlehost, приватна адреса для multi-host (як зараз, але через змінні з дефолтами).

### 4.6 Роль `rabbitmq` (single-режим)

- репо rabbitmq+erlang (keyring-файли);
- `rabbitmq.conf` — повний шаблон (зараз тягнеться з git.webitel.com + патчиться lineinfile; конфіг переносимо в templates/, звіривши з актуальним у WEP/rabbitmq);
- enabled_plugins — файл у ролі;
- юзер webitel, видалення guest, limits drop-in;
- cluster-блоки конфіга рендеряться лише коли `groups['rabbitmq'] | length > 1` (активується у ф.2).

### 4.7 Ролі `webitel_*` (тонкі)

**Конфігурація — редагування env-файла пакета на місці, БЕЗ дублювання і БЕЗ ExecStart-флагів** (рішення 2026-06-11, переглядає попередній підхід):

- кожен webitel-сервіс читає налаштування зі свого env-файла, який **постачає deb-пакет** (напр. `/etc/default/webitel`, `/etc/default/engine`, `/etc/default/webitel-cases`, …). Цей файл — **єдине джерело правди**;
- роль НЕ рендерить власну повну копію env-файла і НЕ перевизначає `ExecStart` через systemd drop-in. Натомість редагує **лише ті ключі**, що відрізняються від пакетних дефолтів (адреси consul/amqp/DSN/opensips), через `lineinfile`-цикл по словнику `webitel_<svc>_env_overrides` (`KEY: value`), keyed на `^#?\s*KEY=`. Так зміна в пакеті не вимагає правок у плейбуку, і немає дрейфу між двома копіями;
- **застереження точності:** назва кожного env-ключа має точно збігатися з пакетною — інакше `lineinfile` допише мертвий рядок, а справжній ключ лишиться з дефолтом (тиха помилка). Тому фактичні імена env-файлів і ключів кожного сервісу 26.4 знімаються Task 9 (VM discovery: `dpkg -L` + `cat /etc/default/*` + unit `EnvironmentFile=`), і ролі будуються вже з реальними іменами;
- `install.yml`: `apt: name=webitel-<x>` — юніт, юзер, enable, restart робить пакет;
- `configure.yml`: `lineinfile`-цикл по `webitel_<svc>_env_overrides` над файлом `webitel_<svc>_env_file` → notify restart відповідних `webitel-*.service`;
- значення override-ів беруться з обчислених group_vars (`webitel_pg_dsn_base`/`webitel_amqp_url`/`webitel_consul_address`/`webitel_opensips_host`), localhost для singlehost; у singlehost словник override-ів зазвичай порожній (пакетні дефолти вже localhost) → роль нічого не міняє;
- **публічний URL відокремлений від nginx**: `webitel_public_url` (те, що бачать користувачі — перед nginx може стояти LB/CDN) — самостійна змінна, яка використовується сервісами (auth URLs, site_url месенджерів, посилання storage); `nginx_site_name` — лише server_name nginx-а та домен для letsencrypt. Дефолт `webitel_public_url` виводиться з nginx-налаштувань, але при LB задається явно; окремо `webitel_srvinfo_url` — адреса для finish-перевірки з контролера.

Набір ролей: common, core (api/app/uac), engine, call_center, flow_manager, storage, messages (srv+bot), logger, cases, media_exporter — базові; portal, fts, wfm, dsa, meetings, webrtc_rec, im (6 сервісів одним пакетом ролей чи окремо — вирішити при імплементації за фактичними пакетами) — опціональні. Усі вмикаються лише наявністю групи в інвентарі.

## 5. Схеми розгортання HA

Підтримувані цільові схеми (всі — один і той самий каркас, відрізняються лише інвентарем):

### 5.1 Failover (один ДЦ)

Схема з Failover-доки: все в одному ДЦ, критичні віртуалки задубльовані, Nomad забезпечує оркестрацію (single-instance сервіси перетікають між нодами, multi-instance живуть скрізь). Один кластер consul (3), patroni (3), rabbitmq (3) на весь інвентар. **Це скоуп фази 2.**

### 5.2 Warm standby, 2 ДЦ

У кожному ДЦ — **свій незалежний кластер** consul, patroni, rabbitmq. Сервіси кожного ДЦ підключаються **лише до інфраструктури свого ДЦ** (DC-locality виходить безкоштовно: всі DSN-и йдуть через локальний consul agent → `*.service.consul` резолвиться в межах свого DC-кластера). Nomad забезпечує оркестрацію. Кворум зберігається в кожному ДЦ незалежно — втрата ДЦ не валить інший.

Міждц-зв'язки (реплікація PG між ДЦ — Patroni standby cluster, синхронізація RabbitMQ — federation/shovel, процедура промоушна standby-ДЦ) — деталізуються у фазі 3.

### 5.3 Warm standby, 3 ДЦ

Patroni **розтягується одним кластером** по трьох ДЦ (розкладка 2-2-1). Оскільки Consul лишається per-DC (його KV не реплікується між ДЦ), DCS для stretch-Patroni — **etcd**, теж розтягнутий 2-2-1. Consul і RabbitMQ — як у 5.2, per-DC. Наслідок: потрібна роль `etcd`, а реєстрація `master./replica.*` сервісів у per-DC consul при etcd-DCS робиться не самим Patroni, а consul-сервісами з HTTP health-чеками на Patroni REST (`:8008/master`, `:8008/replica`) — деталі у фазі 3.

### 5.4 Принцип: схеми — це приклади, код знає лише інваріанти

Названі схеми **не кодуються** (жодного `deployment_scheme: failover|warm_standby`). Вони існують як example-інвентарі (`failover.yml.example`, `warm-standby-2dc.yml.example`, `warm-standby-3dc.yml.example`). Код оперує лише:

- виміром `datacenter` (атрибут хоста, дефолт `dc1`);
- peer-змінними `*_cluster_hosts` (дефолт — члени групи у своєму ДЦ);
- явними ручками там, де вибір реально існує: `patroni_dcs: consul|etcd` (дефолт `consul`), `patroni_cluster_scope: dc|global` (дефолт `dc`).

Будь-яка топологія, що проходить інваріанти нижче — легальна, навіть не описана в прикладах.

**Перевірки preflight** (рядок = ситуація в інвентарі, яку preflight вважає помилкою; зрозумілі повідомлення — частина вимог):

| Помилкова топологія | Чому це проблема | Реакція |
|---|---|---|
| Один consul server-кластер розтягнутий на >1 ДЦ | Consul завжди per-DC; між ДЦ KV не реплікується, стретч ламає модель | fail |
| У ДЦ є хости з сервісами, але немає consul servers у цьому ж ДЦ | сервіси ходять тільки через локальний agent → у своєму ДЦ нема куди приєднатись | fail |
| `patroni_cluster_hosts` охоплює >1 ДЦ, а `patroni_dcs != etcd` (або група `etcd` порожня) | Consul KV не реплікується між ДЦ — stretch-Patroni на Consul DCS не працює | fail |
| etcd не покриває всі ДЦ Patroni, або розкладка не переживає втрату ДЦ (2-2 замість 2-2-1) | втрата одного ДЦ кладе кворум DCS → кластер read-only | fail / warn |
| Один RabbitMQ-кластер розтягнутий на >1 ДЦ | стретч RabbitMQ між ДЦ офіційно не рекомендований (partition-ризики); у warm standby кожен ДЦ має свій кластер | fail; свідомий override `rabbitmq_allow_stretch: true` |
| Один Nomad server-кластер розтягнутий на >1 ДЦ | кворум має переживати втрату ДЦ → servers per-DC | fail |
| Парна кількість нод у server-кластерах consul/nomad/etcd (2, 4) | парний кворум не дає виграшу у відмовостійкості, лише ризик split | warn |
| Більше одного `rtpengine`/`opensips` хоста **в межах одного ДЦ** | поки ці компоненти single-instance per-DC (HA для них — floating IP у ф.3) | fail |

**Структурні інваріанти** (забезпечуються самим дизайном ролей, без перевірок):

- ролі формують кластери з peer-змінних, не з глобальних груп;
- сервіси ходять у залежності тільки через локальний consul agent (127.0.0.1) → DC-locality автоматична;
- `bootstrap_expect` та подібні параметри виводяться з довжини peer-списку, не задаються вручну;
- Nomad — оркестрація у всіх схемах; клієнти позначені своїм `datacenter`.

## 6. Фаза 2 — HA (схема Failover, один ДЦ)

Той самий каркас; режим вмикається інвентарем (`failover.yml`: 3×consul_servers, 3×patroni, 3×rabbitmq, nomad_servers = consul_servers, nomad_clients = всі ноди).

Порядок plays (site.yml вже готовий до цього з ф.1):

1. `base` — всі хости;
2. `consul` servers — `serial: 1` після початкового кворуму; gossip encrypt (змінна з vault), TLS;
3. `consul` agents — всі інші хости, `retry_join` на серверів; **DNS-форвард `.consul` → 127.0.0.1:8600** (unbound або systemd-resolved) — частина ролі, без нього схема `*.service.consul` не працює;
4. `nomad` servers — на нодах `nomad_servers`;
5. `nomad` clients — **всі ноди**: `node_pool` і `meta.services` з host_vars; інсталяція `nomad-systemd-driver-plugin`; consul-інтеграція на локальний agent; TLS той самий CA. Роль закінчується на `nomad node status` ready. **Джобів не деплоїмо**;
6. `patroni` — `serial: 1`: перша нода bootstrap, решта — репліки. Конфіг `/etc/patroni/config.yml`: scope, Consul DCS (localhost agent), bootstrap DCS params, pg_hba, теги `failover_priority` з host_vars. Нативний postgresql unit disabled. Patroni реєструє `master./replica.postgresql-{{ pg_major }}.service.consul`. Створення БД webitel + міграції — тільки на лідері (REST `:8008/leader`);
7. `rabbitmq` cluster — `serial: 1`: спільний `.erlang.cookie` (vault), `/etc/hosts` aliases для нод групи, `cluster_formation.peer_discovery_backend = consul` (host = 127.0.0.1), quorum queues policy;
8. далі voice/webitel/web — ролі ф.1, але DSN-и рендеряться на consul-імена: `master.postgresql-{{ pg_major }}.service.consul`, `rabbitmq.service.consul`, registry `127.0.0.1:8500`. Прапорець `webitel_systemd_enabled: false` — заділ під перехід сервісів під Nomad.

### Поза фазою 2 (свідомо)

- **Фаза 3 — Warm standby (схеми 5.2/5.3) + Nomad jobs**: per-DC інвентарі, роль `etcd` (DCS для stretch-Patroni), Patroni standby cluster між ДЦ, RabbitMQ federation/shovel, consul-реєстрація Patroni при etcd-DCS, Nomad jobs (webitel-app, opensips + floating IP, count-per-node);
- keepalived (KZ-проксі), pgbackrest, моніторинг (Alloy/Loki/Prometheus);
- Molecule-сценарії для consul/patroni/rabbitmq додаються у фазі 2 (converge + idempotence).

### Рішення фази 2 (узгоджено 2026-06-11)

- **Скоуп фази 2:** HA-ролі, що працюють у двох режимах інвентаря — Failover (1 ДЦ, один кластер на 3 ноди) і Warm standby 2 ДЦ (per-DC кластери, дають дві незалежні HA-інсталяції). **Крос-ДЦ реплікація даних (Patroni standby cluster, RabbitMQ federation) — лишається фазою 3**; 2-ДЦ у фазі 2 = два самостійні кластери без автоматичної синхронізації між ними.

CA-ключ зберігається на контролері (`inventories/<env>/pki/`, у `.gitignore`).
- **nomad-systemd-driver-plugin:** змінна `nomad_systemd_driver_install: apt|url|none` (дефолт `none`). Кластер Nomad піднімається без джобів незалежно від плагіна (джоби — фаза 3). Референс `patroni-cluster/nomad-client.sh` ставить пакет `nomad-driver-systemd` через apt — це режим `apt`.
- **Запуск:** користувач проганяє `site.yml` сам (контролер має доступ до VM + секрети); агент лише постачає код, інвентар-приклади та інструкції.
